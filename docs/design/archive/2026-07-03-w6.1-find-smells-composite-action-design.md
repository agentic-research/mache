# W6.1 — Reusable `find-smells` composite GitHub Action

- **Bead:** `mache-4dbad9`
- **Decade / thread:** analysis-substrate → W6 (distribution)
- **Date:** 2026-07-03
- **Depends on:** W5.3 (`task smells` local-first ratchet gate, merged, v0.11.0)

## Problem

W5 shipped the structural smell **ratchet gate** as a local/CI concern *inside*
mache: `task smells` builds a tree-sitter `.db`, runs
`find-smells --rule '*' --baseline docs/smell-baseline.json`, and fails on
new-vs-baseline findings. That gate only runs on mache's own tree.

W6 (distribution) asks: **how does any other repo consume the same gate?** The
deliverable is a reusable composite action at
`.github/actions/find-smells/action.yml` that a consumer wires up as:

```yaml
- uses: agentic-research/mache/.github/actions/find-smells@<sha>
```

The existing `.github/workflows/find-smells.yml` is **not** this — it is a
mache-internal *advisory* PR-comment workflow (never gates), and is now
superseded by the W5.3 `task smells` gate.

## Ground-truth constraints (verified)

1. **`find-smells` emits `json` / `md` / `ci` only — no SARIF.**
   (`cmd/find_smells_cli.go:548`; `renderFindings` is a hardcoded `md`/`json`
   switch at `:465`.)
1. **Released binaries are CGO-enabled** (`release.yml:68` `CGO_ENABLED: '1'`),
   so `mache-linux-amd64` **has tree-sitter** and can parse raw source via
   `--backend tree-sitter`. The "CGO-free" note in `release.yml` refers only to
   the leyline_fs/FUSE symbols, not tree-sitter. → A consumer can download the
   prebuilt release binary and scan raw source; no build-from-source needed.
1. **Consumer repos have no `docs/smell-baseline.json`.** The ratchet is
   meaningless without a committed baseline, so the action must define
   missing-baseline behavior.

Release publishes `mache-darwin-arm64`, `mache-linux-amd64`, `mache-linux-arm64`
via `softprops/action-gh-release` (`release.yml`).

## Design

Two components. Component 1 lands and ships in a release first; Component 2
pins to that release (bootstrap ordering, see Sequencing).

### Component 1 — `find-smells --format sarif` (mache-native, template-driven)

Add `sarif` to the format switch in `cmd/find_smells_cli.go`. SARIF differs
from `md`/`json` (which emit one envelope **per rule**): it renders **once over
all rules** —

- `runs[0].tool.driver.rules[]` from the rule registry (`cmd/smell_rules.go`)
- `runs[0].results[]` from the flattened finding set (`allFindings(results)`)

Rendered via an **embedded Go template** (`cmd/schemas/sarif.tmpl`) passed
through the existing `internal/template.Render` engine. The func map already
provides what SARIF needs (`json` for string escaping, `dict`, `dig`). SARIF is
therefore **data-driven, not bespoke Go** — the "schema engine does it" path,
consistent with mache's projection thesis. No SARIF library dependency.

**Rejected — generic `--template FILE` flag:** more surface, and consumers
would have to carry a template file. Embedded `--format sarif` keeps the
consumer contract trivial. A generic `--template` is a clean future
generalization (YAGNI now).

**SARIF field mapping (2.1.0):**

| SARIF path                                                    | Source                                      |
| ------------------------------------------------------------- | ------------------------------------------- |
| `runs[].tool.driver.name`                                     | `"mache find-smells"`                       |
| `runs[].tool.driver.rules[].id`                               | `SmellRule.ID`                              |
| `runs[].tool.driver.rules[].shortDescription.text`            | `SmellRule.Description`                     |
| `runs[].tool.driver.rules[].defaultConfiguration.level`       | `SmellRule.Effective()` → `warning`/`error` |
| `results[].ruleId`                                            | finding's rule ID                           |
| `results[].level`                                             | rule severity                               |
| `results[].message.text`                                      | rule description (+ metric)                 |
| `results[].locations[].physicalLocation.artifactLocation.uri` | `finding.SourceID` (baseline-root-relative) |
| `results[].locations[].physicalLocation.region.startLine`     | `finding.Line`                              |
| `results[].locations[].physicalLocation.region.startColumn`   | `finding.Column`                            |

Paths are relativized the same way the ratchet already relativizes
(`relativizeFindings(..., findSmellsBaselineRoot)`) so SARIF URIs are
repo-relative and portable — GitHub code-scanning resolves them against the
checked-out tree.

### Component 2 — `.github/actions/find-smells/action.yml` (composite)

Steps the consumer inherits:

1. **Install** — `curl -sSfL` the pinned `mache-linux-amd64` release asset for
   `inputs.mache-version`, `chmod +x`, place on PATH. No Go / CGO / LFS in
   consumer CI.
1. **Baseline guard** — if `inputs.baseline` (default `docs/smell-baseline.json`)
   does not exist → **fail-loud**, exit non-zero with the exact bootstrap
   command:
   `mache build . smells.db && mache find-smells --db smells.db --rule '*' --write-baseline docs/smell-baseline.json`
   and "commit it, then re-run".
1. **Build .db** — `mache build [--schema <inputs.schema>] . repo.db`
   (`--backend tree-sitter` is available in the CGO=1 release binary; omit
   `--schema` to use FCA inference).
1. **Gate** — `mache find-smells --db repo.db --rule '*' --limit 100000 --baseline-root "$PWD" --baseline <inputs.baseline>`. Non-zero exit on
   new-vs-baseline = the W5 ratchet, now portable. Gated by
   `inputs.fail-on-new` (default `true`).
1. **Report** — `--format md` to `$GITHUB_STEP_SUMMARY`; when
   `inputs.upload-sarif` (default `true`), also `--format sarif` → upload via
   `github/codeql-action/upload-sarif` (SHA-pinned) → findings land in the
   consumer's Security / code-scanning tab.

**Inputs:**

| Input           | Default                                              | Meaning                              |
| --------------- | ---------------------------------------------------- | ------------------------------------ |
| `mache-version` | pinned release tag (the first with `--format sarif`) | release asset to download            |
| `schema`        | *(empty → FCA infer)*                                | path to a topology schema            |
| `baseline`      | `docs/smell-baseline.json`                           | committed ratchet baseline           |
| `fail-on-new`   | `true`                                               | gate the job vs advisory-only        |
| `upload-sarif`  | `true`                                               | emit SARIF + upload to code-scanning |

### Sequencing (bootstrap wrinkle)

The action downloads a **released** binary, so `--format sarif` must exist **in
a release** before the action's SARIF step works. Order:

1. Merge Component 1 (`--format sarif`).
1. Cut a release (v0.11.1 / v0.12.0) that includes it.
1. Merge Component 2, `mache-version` default pinned to that tag.

Until (2), the action can gate + md-summary against v0.11.0; the SARIF-upload
step activates only at the sarif-bearing release.

## Testing

- **C1:** `cmd/find_smells_sarif_test.go` — golden-file test asserting valid
  SARIF 2.1.0 structure and correct rule→driver / finding→result mapping over a
  multi-rule fixture (reuse existing find-smells test DB fixtures).
- **C2:** the existing `cmd/actions_pin_lint_test.go` gates action `uses:` SHA
  pins — the new action's refs (`checkout`, `codeql-action/upload-sarif`) must
  pass it. Add a lightweight assertion that `action.yml` parses and its steps
  reference the declared inputs (no undeclared `inputs.*`).
